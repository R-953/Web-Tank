# War Thunder 风格浏览器载具对战游戏

> 项目文档:写给项目负责人和所有参与开发的 Agent(Claude Code / Gemini / Copilot / Codex 等)。
> Agent 的「干活守则」(命令、禁区、分支、回报格式)在 [AGENTS.md](AGENTS.md),任务看板在 [docs/tasks/](docs/tasks/README.md)。
> 这里只写**长期有效**的内容:目标、范围、技术栈、目录与数据结构约定、协作规则。
> 每一轮做了什么、为什么这么做、还有哪些待确认,以及路线与进度清单,写在 [Changelog.md](Changelog.md)。

## 项目背景

独立开发者,单人,不做手动编码,完全依靠 Coding Agent 实现。目标周期约一年。灵感来自《战争雷霆》(War Thunder)的载具对战机制,但**不追求 1:1 还原**——那个工作量不现实。最终目标缩小为:**一款能在浏览器里直接打开、玩起来有"载具对战"核心手感的 Web 游戏**。

## 声明(declaration)

写清楚"不做什么",和"要做什么"同样重要,避免 agent 自己把范围越写越大:

- 不做诸兵种合成(坦克+飞机+军舰联动),先专注**一种载具类型**
- 简化真实弹道学 / 精细装甲穿透模型,伤害模型追求"手感对"而不是"物理精确"
- 不做全球匹配 / 排位 / 大规模服务器集群,先做**房间制小规模对战**(甚至先做单机 vs AI)
- 简化建模精度,走**低多边形 / 程式化风格**,优先用免费资源库(如 Kenney.nl)而不是定制建模,但不做像素风
- 不做经济系统 / 载具解锁树 / 付费系统,这些留到核心玩法验证之后再说
- 同一车型的早期型和后期型只是换皮时,只做后期型(例如 M4A3(76)W 只做 HVSS);只有差别大到算不同车时才分开做(例如 M4A1(75)W 和 M4A3E2)

## 技术栈(先定死,阶段 0 内不要中途更换)

| 层 | 选型 | 理由 |
|---|---|---|
| 渲染 | Three.js | 生态最成熟,文档/案例最多,agent 查资料容错率高 |
| 物理 | Rapier(WASM,`@dimforge/rapier3d-compat`) | 性能好,有现成的载具物理控制器可参考 |
| 语言 | TypeScript | 类型约束对"多次迭代、多个 session 接手同一份代码"更友好 |
| 构建工具 | Vite | 配置简单,热更新快,适合快速试错 |
| 测试 | Vitest + jsdom | 与 Vite 同一套配置 |
| 联机 | 暂不实现 | 阶段 0 只做单机/本地,联机架构留到阶段 1 再决定 |

> 选型由项目负责人决定;改完之后同样要"钉死",不要让 agent 在开发过程中自行更换核心依赖。

## 快速开始

需要 Node.js ≥ 22.12(Vite 8 / Vitest 5 / jsdom 30 的要求)。

```bash
npm install
npm run dev      # 本地开发服务器,浏览器打开终端里显示的地址
npm test         # 全部测试
npm run build    # 生产构建,输出到 dist/
```

地址栏加 `?debug` 后,可以在浏览器控制台用 `__debug.game()` 查看对局状态,`__debug.advance(秒)` 不渲染直接快进(自动化测试用)。

## 操作

打开页面是主界面(机库):底部是编组栏(按国家选车组、分车、打开科技树),顶部选地图。鼠标放在车上会出现信息卡(双击关闭)。右键(或点卡片上的 ▾)是车组菜单:换车、改装(机动 / 防护 / 火力三栏、每栏 I–IV 级,免费、立即生效;目前只有方向机、高低机、转向、加速和极速几项真的改数值,其余标「效果暂未接入」)、涂装(每辆车 2–4 个历史上用过的涂装方案,机库里实时预览)、试驾(在选好的地图上自由开,靶车不还击、打光也不结束)、乘员(车组等级、技能表、车内乘员站位)。点「进入战斗」先进地图界面:在这里调携弹、选出战的车组,点「出战」才开局;Esc 回机库。你击中敌人后会在右上角回放这一发(跳弹、未击穿、击穿没击毁都有,顶部文字随损伤分级:命中 / 引燃 / 重创 / 乘员昏迷 / 弹药殉爆);**自己被击毁时,回放直接叠在游戏世界里**(残骸变 X 光、弹道线、弹着标记、相机绕残骸环绕),被击中但没被击毁不播;设置 → 游戏里可以关掉、只留击毁,或把死亡回放改回全屏窗口。按 O 直接在当前车上开 X 光看每个模块和乘员(设置里可改回左侧面板)。战斗中底部按钮栏上方是状态提示(起火、发动机 / 传动 / 炮闩 / 炮管受损、乘员昏迷)和圆环进度(乘员顶替、维修,维修倒计时是最下面一行);按钮栏每个按钮有图标;右侧是击毁提示流(射击者车型 ➡弹种 被击毁者车型),左下角是帧率 / 延迟 / 丢包 / 对局 ID 小字(单机没有网络,延迟和丢包恒为 0;设置里可关)。战斗中按 M 随时打开大地图(对局继续跑),再按 M / Esc / 点「返回战斗」回去。左上角 ☰ 菜单里是设置(游戏 / 图像 / 声音 / 操作),符号体系(北约 / 华约)也在这里或地图界面右侧选。

默认键位如下。**全部可以在「设置 → 操作」里改**(键盘、鼠标五个键、滚轮上 / 下都能绑,每个操作两个键位),也可以直接导入 War Thunder 的操作设置文件(`.blk`,只导入单键的坦克操作)。

| 主炮开火 | 鼠标左键 |
| 同轴机枪 | 空格(按住连发) |
| 切换弹种 | 1 – 4;Caps Lock 切到下一种 |
| 显示 / 关闭车内结构(模块、乘员、岗位,实时) | O |
| 开镜 / 关镜 | Shift |
| 瞄准镜倍率 / 第三人称放大 | Z 循环(视场平滑过渡);PgUp / PgDn 放大 / 缩小 |
| 表尺 | 滚轮:往下滚加远,往上滚减近 |
| 维修 / 取消维修 | F |
| 灭火 | 6 |
| 显示光标操作小地图 | 按住左 Alt:滚轮缩放小地图,双击标点(再双击取消);此时键盘照常,鼠标上的操作停用 |

## 核心数据结构约定

这些一旦定下,后续所有内容都要复用,不要每加一个载具 / 地图就重新设计一遍格式。类型定义都在 `src/data/types.ts`。

- **载具** `VehicleSpec`:`{ id, name, armor, turretArmor, maxSpeed, turretRotationSpeed, weapons, hull, turret, sight, internals, color }`
  - `armor` / `turretArmor` 为 `{ front, side, rear }`,填水平来弹的视线厚度(倾斜装甲按 t / cos 倾角换算)
  - `hull` 车体尺寸与机动,`turret` 炮塔尺寸、炮管长、俯仰范围、高低机速度,`sight` 瞄准镜倍率与分划样式
  - 可选的展示字段 `mass`(战斗全重 kg)、`enginePower`(`{ hp, rpm }`)、`reverseSpeed`(km/h):只显示在信息卡上,不参与物理
  - 改装和涂装不改 `VEHICLES` 里的原始数据:进战斗时由 `applyModifications` / `applyPaint` 套出一份新的 `VehicleSpec`,经 `GameConfig.playerSpec` 只交给玩家那一辆(同型号的靶车 / 敌车不受影响)
- **武器与弹药**:`weapons[i] = { id, name, reloadTime, ammo: ShellSpec[], kind? }`,`weapons[0]` 是主炮,`ammo` 第一项是默认弹
  - 同轴机枪 `kind: 'mg'`,另有 `rateOfFire`(发 / 分)、`beltSize`(每条弹链)、`rounds`(总发数)、`mount`(火炮坐标系里的枪口位置);`reloadTime` 是换弹链时间,机枪弹不占弹药架
  - 口径 < 20 mm 的弹按枪弹处理:打不坏坦克(只判跳弹 / 未击穿),能削灌木,被树干挡下
  - `ShellSpec = { id, name, type, caliber, mass, muzzleVelocity, penetration, explosiveMass, fuseDelay, fuseSensitivity, dragCoefficient? }`
  - 弹种 `type`:实心穿甲弹 AP / APC / APBC / APCBC,带装药穿甲弹 APHE / APHEBC / APCBC-HE,硬芯弹 APCR,化学能弹 HEAT / HE / HESH
  - 动能弹的 `penetration` 是炮口穿深(随弹速衰减),化学能弹的是固定值;各弹种的通用规则(入射角、跳弹、阻力、击穿后效)在 `src/data/shells.ts`
- **内部结构** `internals = { modules, crew }`
  - 模块 `{ id, type, part, center, size }`,`part` 为坐标系(hull / turret / gun,见 `AttachPart` 注释);弹药架另有 `capacity`(发数)和 `drawOrder`(取弹顺序,1 最先取空)
  - 乘员 `{ role, part, center }`,五个岗位:车长、炮手、装填手、驾驶员、机电员
  - 模块 / 乘员的血量、维修时间按类型统一定义在 `src/data/modules.ts`,击穿后效的调参值在 `src/data/damage.ts`;加新车只需要摆盒子
- **携弹方案** `Loadout = { [弹种 id]: 发数 }`
- **地图** `MapSpec = { id, name, size, terrain, surface?, waterLevel?, obstacles, spawns }`
  - `terrain = { cellSize, base, heightmap?, features }`:地形由「要素列表」描述(hill / mountain / ridge / plateau / dunes / valley),加载时按顺序叠加成高度网格;小地图也可以用手写字符高度网格。手写、确定性,**不做随机生成**
  - `vegetation = { zones, grass?, clearRadius? }`:植被区(圆或多边形)+ 密度(株 / 公顷)+ **固定种子**撒点,每次加载位置完全一样(确定性,不是每局随机);水面、陡坡、障碍物、出生点和巡逻路线附近自动跳过。画质里的「植被密度」只做确定性抽稀。草丛按地表自动铺,只在镜头附近生成
  - `surface`:手写字符网格标地表类型(草地 / 土地 / 沙地 / 岩地 / 泥滩 / 浅水 / 积雪),决定颜色和滚动阻力(`src/data/surfaces.ts`)
  - `spawns`:玩家与敌方出生点,敌方可选巡逻路线、是否还击、携弹比例
- **伤害模型**:没有整车血量。
  - 命中面装甲 → 等效装甲(按弹种的入射角规则)→ 跳弹判定 → 击穿判定
  - 击穿后在车内模拟弹体 / 射流、崩落破片、装药爆炸,扣对应模块和乘员的血
  - 模块和乘员受伤都按血量比例降低性能,例如发动机半血 → 功率减半,装填手半血 → 装填速度减半
  - 打坏的模块按 F 维修;乘员阵亡后由他人顶岗
  - 存活乘员少于 2 人,或弹药架殉爆,即判定摧毁;殉爆概率随该弹药架剩余弹数升高
  - 炮闩 / 炮管受损(没报废)时开炮有概率击发失败(估算:0.5 ×(1 − 模块血量比例),1 秒冷却)
  - 发动机 / 油箱受损可能起火:火烧附近的模块和乘员,烤久了引燃弹药架;按键灭火(灭火器有限),敌方 AI 过几秒自己灭火
- **敌方 AI 强度** `AI_PRESETS`(`src/data/ai.ts`):`training` 训练(默认,宽松)与 `guard` 守卫(第四轮的原始参数,留给以后的守卫模式)
- **设置** `GameSettings`(`src/settings/Settings.ts`):`{ game, graphics, sound, controls }`,读入时逐项修正(旧存档缺字段、越界值都会回到缺省);键位 `Bindings = { [操作 id]: [主键位, 副键位] }`

## 编码与测试规范

- 每个功能落地前,先写一个能验证它的最小测试(哪怕只是"载具能不能移动""子弹能不能命中")
- 新增模块前先检查 `/src` 下是否已有类似功能可复用,避免重复造轮子
- 数值来源按顺序:① 公开资料,出处写在代码注释或 `docs/physics-validation.md`;② 公开资料查不到或查不准时,用 [War Thunder 官方 wiki](https://wiki.warthunder.com/) 的设定,注明「War Thunder 值」;③ 两者都没有时,已有的值保持不变,新数据才允许估算,在代码注释里标明「估算」并写出估算方法
- 物理 / 规则代码尽量写成不依赖渲染的纯函数或类,方便在测试里直接跑(`Game.fixedUpdate` 可以脱离浏览器运行)

## 协作约定(所有 Agent 都要遵守)

- **开工前先读 AGENTS.md、本文件和分配给你的任务卡**(`docs/tasks/`),需要背景时再看 Changelog.md 最近几条
- **架构级选择先问项目负责人**:换依赖、改核心数据结构(上面列出的格式)、重构伤害模型这类决策,不要自己决定完就直接大量铺代码
- **局部实现可以自主决定**:函数命名、工具类拆分、调参细节等
- **每个任务写一条 `changelog.d/`**,每轮结束由主程汇总进 Changelog.md(按日期倒序,写清新增 / 变更 / 修复、决策及理由、待确认);改了数据结构要同步更新本文件
- 完成路线清单(Changelog.md 开头「路线与进度」)里的一项就更新勾选状态
- 合并前全部测试必须通过

### 多智能体分工(2026-09-29 起试行)

一个主程加几条执行车道,优先用其他家的额度,Claude 作为中枢节点。核心系统不并行。

**派发方式:** 主程用 `scripts/agents/dispatch.mjs` 从终端把任务卡派给各个 agent(一个任务一个 worktree,受限权限,并行跑),跑完自动评分、出报告,主程审查后再开 PR。用法见 [scripts/agents/README.md](scripts/agents/README.md),各家模型的测试见 [docs/research/model-bench-2026-10.md](docs/research/model-bench-2026-10.md)。

| 车道 | 工具 | 负责 |
|---|---|---|
| 主程 / 集成 / 审查 | Claude Code | 拆任务、写任务卡、用调度脚本派发、审查、修冲突、合并;核心规则(伤害、弹道、`Game` / `Vehicle` 主循环)和数据结构。其他 agent 都做不了的才亲自写 |
| 内容 / 界面 / 实测 | Antigravity(默认 Gemini 3.8 Flash High,第二选择 Claude Opus 4.6) | 新车数据调研(带出处)、按零件库做模型、界面打磨、在真浏览器里截图验收、性能测量 |
| 小任务 / 审查 | GitHub Copilot | 边界清楚的小逻辑 / 小 bug、补测试、PR 审查。目前只有 mai-code-1.1-flash,2026-10-03 权益生效后重测 |
| 待定 | Codex CLI | 等 OpenAI 回复工单 |
| — | 本地模型(LM Studio) | 能力不够,暂不派活(见任务 004) |

规则:
- **数据结构冻结:** 核心数据结构只加可选字段,要改结构先单独提出。
- **分支与合并:** 一个任务一个分支(并行时各用一个 git worktree),通过 PR 合并,CI 必须通过。
- **热点文件:** 归主程,清单见 AGENTS.md。
- **额度:** 同一个 Claude 订阅下,Claude 的各个产品(网页 / 桌面 / Cowork / Code)共用一份用量。不要在 Cowork 和 Code 里同时推进同一件事。长会话每一轮都更贵,一个任务做完就开新会话,靠仓库里的文件交接。
